# AppleSupport agent: evaluation report

## Problem framing

This is a conservative public-Twitter triage assistant for **AppleSupport**, not
a replacement for Apple Support or a device repair diagnostic tool. “Good” is:
identify a customer's operational need, offer a historically grounded public
reply when it is plainly safe, and otherwise get the message to a human with a
specific reason. The intended benefit is faster acknowledgement of routine
questions, not resolution at all costs.

Not built: authentication, account lookup, order/refund handling, diagnostic
steps that depend on device state, automated repair decisions, multilingual
coverage, or background follow-up. TWCS is historical and anonymized; it cannot
establish current Apple policy.

## Data and method

The official TWCS release produced 106,623 direct inbound-customer →
AppleSupport reply pairs. A TF-IDF (word 1–2 gram) logistic-regression intent
classifier is trained on transparent bootstrap labels. For a possible automatic
reply, the agent retrieves the closest *training-only* message with the same
intent and reuses its historical AppleSupport reply. It automatically sends only
generic how-to/compatibility responses with confidence ≥0.80, cosine evidence
≥0.34, and no sensitive-risk term. Everything else is escalated.

The 175-row golden set is a fixed-seed stratified sample of real incoming TWCS
messages. Its source IDs are excluded from training and retrieval. Full sampling
and labelling rules are in `docs/labeling_protocol.md`.

## Results

Results below are regenerated by `make evaluate` using
`data/golden_apple_v1.jsonl`.

| System | Macro F1 | Accuracy |
|---|---:|---:|
| Trivial: always `other_needs_human` | 0.010 | — |
| Simple: transparent keyword router | 0.691 | — |
| TF-IDF + logistic regression | 0.691 | 0.766 |

The learned classifier matches, rather than improves on, the keyword baseline.
That is unsurprising and a warning: bootstrap labels were created from related
lexical rules. The routing policy auto-handles just 3.4% of the golden set,
with 0.500 precision and 0.214 recall for the deliberately narrow
`auto_handle` label. Low coverage is intentional, but it also means this is not
an automation-coverage success story.

Reply evaluation is designed as an LLM-as-judge audit, not BLEU/ROUGE. The
rubric scores (1) precedent-grounding/no invented promise, (2) helpful next
step, and (3) safe handling/routing. The judge receives the message, decision,
draft, and retrieved evidence but no gold intent. `scripts/judge_replies.py`
uses a zero-temperature JSON schema and reports Cohen's kappa against a 50-row,
independently human-scored calibration subset.

**Judge agreement status: not yet measured.** The calibration rows are present,
but intentionally blank rather than fabricated. This is a hard pre-production
gate: obtain a second reviewer and run the script with a model API before making
any trust claim about the judge. Thus the pipeline includes the required test,
but this submission does not claim human/LLM agreement evidence it does not
have.

## Failure analysis

| Failure mode | Real golden example (tweet ID) | Hypothesis / mitigation |
|---|---|---|
| Hardware vs software confusion | `595801`: iPod stuck at Apple logo and not recognized | Keyword “charge” proposes battery; review makes it hardware. Add component/state features and repair-labelled examples. |
| Account language hides a sync defect | `2509366`: new iPhone photo-library sync hiccups | “iCloud” is often identity/billing but this is functional. Add conversation context and a separate sync intent if volume justifies it. |
| Data loss has overlapping meanings | `2341938`: photos deleted after reset | A recovery question is labelled security/privacy for routing safety; semantic intent differs from safe action. Separate *topic* and *risk* heads. |
| Ambiguous follow-up tweet | `2372229`: “It did after restarting/charging” | The first message is missing, so intent cannot be inferred. Retrieve thread context or always human-route replies without context. |
| Product-specific response gets overgeneralized | `1709976`: low earpiece audio after update | Update and hardware symptoms overlap. Require device/model and tested-step slots before offering a public action. |

## What is misleading about my headline number?

Macro F1 0.691 looks respectable beside 0.010, but it is **not a deployment
claim**. The golden set is small (175), author-labelled, and stratified from a
queue seeded by lexical rules related to the weak training labels. It overstates
certainty about natural traffic. Accuracy is also helped by common, obvious
classes. Critically, no LLM-judge/human agreement or live safety review is yet
reported. The model does not beat the simple keyword baseline, and a close
historical reply is not proof that the reply is currently correct.

With a further week: independently double-label 300–500 temporally held-out
messages and adjudicate disagreements; label risk separately from topic; gather
current approved Apple public-support guidance; compare a small instruction
model with retrieval; tune thresholds on a separate validation set; and run a
shadow mode with agent QA measuring harmful-auto-route rate, escalation quality,
and resolution proxy rather than text overlap.
